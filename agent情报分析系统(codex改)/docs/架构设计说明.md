# 架构设计说明

## 四层架构总览

```
┌─────────────────────────────────────────────────────────┐
│  用户交互层                                              │
│  移动端网页 · 对话工作台 · 工作流图 · BI报表 · 证据关系图    │
│  React + TypeScript + ECharts                            │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  应用服务层                                              │
│  任务API · 工作流编排 · 身份与权限 · 任务状态持久化         │
│  Python + FastAPI + Pydantic                             │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  Agent与检索层           │  分析与算法层                    │
│  研究执行Agent           │  统计分析（Pearson/Bootstrap）  │
│  RAG检索                 │  因果审查（Granger/DID/IV）     │
│  工具调用                │  预测模型（ARIMA/Prophet）      │
│  证据综合                │  运筹优化（LP/MIP）             │
│  LLM推理                 │  异常检测（IQR/Z-score）        │
└─────────────────────────────────────────────────────────┘
                           ↓
┌─────────────────────────────────────────────────────────┐
│  数据与治理层                                            │
│  SQLite → PostgreSQL · 证据登记 · 预测登记 · 审计日志      │
│  权限治理(M14) · 承诺等级(M21) · 模型健康(M20)             │
│  确定性规则引擎，不由LLM控制                               │
└─────────────────────────────────────────────────────────┘
```

## 核心设计决策

### 1. 确定性治理层（修正问题1）

**问题**：M21被重复分配了权力，既是共享服务，又说最终裁决必须留在主控Agent。

**解决方案**：三层分离

- **第一层：子模块提供依据**
  - 报告数据质量、模型表现、证据冲突、验证结果和失败情况
  - 不自行提高结论的可信等级

- **第二层：确定性规则引擎执行M21**
  - 依据可配置的规则、证据门槛、验证结果和权限约束
  - 计算允许的最高承诺等级
  - 由普通代码实现，不由LLM控制

- **第三层：主控Agent负责最终交付**
  - 根据裁决结果组织报告
  - 不得擅自提高等级
  - 遇到规则未覆盖的情况，进入复核或降级流程

**关键区别**：如果M21只是一个提示词，要求大模型"谨慎判断"，它仍可能自相矛盾。关键规则应由普通程序执行，LLM负责提供分析依据，而不是拥有绕过规则的权力。

### 2. 不按模块创建独立Agent（修正问题2）

**问题**：按每个模块创建独立Agent，听起来专业，但实际未必划算。

**解决方案**：执行单元划分

| 执行单元 | 实现方式 | 核心原因 |
|---------|---------|---------|
| 主控编排层 | 工作流引擎 + 主控Agent | 管理任务状态、依赖、失败恢复 |
| 研究执行单元 | 研究Agent + 工具函数 | 需要结合上下文多步判断、处理不确定性 |
| 分析执行单元 | 分析Agent + 算法库 | 需要动态选择工具、综合多源证据 |
| 治理验证层 | 确定性代码服务 | 不能让Agent自己决定是否绕过权限/承诺等级 |

**原则**：能由普通代码稳定完成的工作，不要为了追求Agent数量而交给LLM。

### 3. 关键模块不是普通子Agent（修正问题3）

| 模块 | 更合理的实现形态 | 核心原因 |
|-----|---------------|---------|
| M8 预测登记与结算 | 数据库服务 + 结算规则引擎 | 需要不可随意覆盖的预测记录和可复核的结算过程 |
| M14 权限治理 | 权限服务 + 确定性策略执行器 | 不能让Agent自己决定是否绕过权限 |
| M19 Agent状态机 | 工作流编排器 + 持久化状态机 | 需要管理重试、超时、依赖、失败和恢复 |
| M20 模型健康 | 监控任务 + 统计检测模块 | 漂移检测和版本回滚应当有明确的触发条件 |
| M21 承诺等级 | 规则引擎 + 裁决记录 | 等级变化必须有依据、可追踪、可复核 |

这些模块可以拥有独立的接口，甚至单独部署，但有独立接口不等于需要独立的大模型Agent。

### 4. 任务协议设计（修正问题4）

**问题**：结构化JSON还不够，必须设计任务协议。

**解决方案**：TaskContract包含完整字段

```python
class TaskContract(BaseModel):
    task_id: str              # 任务唯一标识
    task_type: str            # 任务类型
    input_data: Dict          # 输入数据
    input_hash: str           # 输入内容哈希，用于追溯
    method_version: str       # 方法版本
    created_at: datetime
    started_at: datetime
    completed_at: datetime
    status: TaskStatus        # 成功、失败、部分成功、熔断等
    evidence_refs: List[str]  # 产出的证据引用
    error_code: str           # 错误类型
    retryable: bool           # 是否允许重试
    output_hash: str          # 输出内容哈希
    commitment_level: CommitmentLevel
    permission_level: PermissionLevel
```

**配套机制**：
- **幂等性**：同一任务因超时重试，不应重复登记同一条预测
- **版本化**：Schema变化后，旧任务仍应能够读取和审计
- **持久化**：手机应用退出、进程被系统回收后，可以恢复任务状态
- **证据溯源**：报告中的结论必须能够追溯到具体证据、分析方法和模型版本

### 5. 预测验证闭环（修正问题5）

**问题**：预测登记、结算、校准的完整闭环不够清晰。

**解决方案**：六步闭环

1. **提出预测**：明确事件、时间范围、概率、前提与适用条件
2. **冻结登记**：保存原始预测、时间戳、证据版本及当时的信息边界
3. **持续监测**：收集新证据，记录前提变化与反证，不覆盖原始预测
4. **独立结算**：事件到期后按预先定义的规则判定结果
5. **回测与校准**：检查Brier Score、校准度、基线差异与错误来源
6. **更新模型**：经过版本化评估后再调整参数，并保留回滚能力

**关键细节**：
- 预测登记应保存当时的信息集，避免未来证据反过来污染过去的预测
- 模型不能只凭自己过去的成功案例证明自己有效，应与简单基线比较
- 累计至少100条已结算预测后开始系统性复盘

### 6. 分层扩展架构（修正问题6）

**问题**：不应直接上10+ Agent，应分层扩展。

**解决方案**：

- **P0：先验证闭环**
  - 1个主控 + 1-2个逻辑执行Agent + 确定性治理服务
  - 先跑通采集、证据追踪、基线预测、独立验证和预测结算

- **P1：根据瓶颈拆分**
  - 如果采集耗时明显、模型评估需要隔离，或告警任务必须独立运行
  - 再拆出研究、建模、验证和监测执行单元

- **P2：扩展专业协作**
  - 在实际任务量和验证结果证明其价值后
  - 再引入知识图谱、因果识别、运筹优化、仿真推演、多模型交叉审查

**拆分原则**：依据实际测得的并发收益、调用成本、故障隔离需求和维护成本，而不是预先规定最终一定要有多少个Agent。

## 手机端适配策略

### 不能假设的条件

- 手机上Python进程可以始终驻留
- Android后台任务可以长期运行
- 本地可以承担全部长期运行任务

### 推荐策略

1. **手机作为入口**：编辑代码、管理Git仓库、展示结果
2. **云端承载重计算**：调用云端运行环境执行长时间任务
3. **本地轻量存储**：SQLite持久化任务状态、支持断点恢复
4. **API客户端**：通过统一模型调用接口接入LLM
5. **断点续传**：任何环节中断可恢复，重要信源无遗漏

### 技术选型

| 组件 | 手机端 | 云端 |
|-----|--------|-----|
| Python | 编辑、调试 | 运行分析算法 |
| SQLite | 存储任务状态 | 按需升级PostgreSQL |
| LLM API | 调用 | 常驻服务 |
| 统计分析 | 轻量任务本地执行 | 大规模计算转云端 |
| 前端 | 手机浏览器 | 部署服务 |

## 数据流与状态管理

### 数据流

```
用户任务 → M1采集 → M2治理 → M3 EDA → M5因果审查
         ↓
    证据登记(M12) ← → 承诺等级评估(M21)
         ↓
    M8预测登记 → 监测 → 结算 → Brier Score
         ↓
    M13报告生成 → 用户交付
```

### 状态管理

- **任务状态**：pending → running → success/failed/partial/circuit_break
- **承诺等级**：A/B/C/D/BLOCKED（只能降级，不能升级）
- **权限等级**：L1/L2/L3（单向收紧）
- **预测状态**： unsettled → settled（hit/miss/falsified/unresolved）

### 持久化策略

- **SQLite**：任务、证据、预测、审计日志
- **文件存储**：原始数据、模型文件
- **断点恢复**：任务checkpoint、输入哈希、方法版本

## 安全与治理约束

### 贯穿各层的约束

1. **权限不可越权放宽**：M14确定性规则引擎
2. **证据可追溯**：每条证据都有source_url、content_hash、extracted_at
3. **失败状态可见**：TaskStatus、error_code、retryable
4. **预测记录可复核**：只追加、不覆盖、保存证据快照
5. **关键结果必须经过验证**：承诺等级评估、独立验证闭环

### 审计日志

所有关键操作都记录审计日志：
- 承诺等级变化
- 权限检查
- 预测登记与结算
- 熔断触发
- 任务状态变化

## 扩展性设计

### 预留扩展点

1. **数据库**：SQLite → PostgreSQL（按需升级）
2. **消息队列**：任务表 → RabbitMQ/Kafka（跨服务并行调度时）
3. **知识图谱**：SQLite关系表 → Neo4j（复杂实体解析时）
4. **分布式计算**：本地 → Spark/Flink（大规模数据时）

### 插件化架构

- **分析算法**：每个算法都是独立插件，有适用条件、失败路径、标准算例
- **工具调用**：统一工具接口，可插拔扩展
- **连接器**：外部数据源通过连接器接入，不影响核心流程

## 总结

本架构设计的核心思想：

1. **确定性治理**：关键规则由普通代码实现，不由LLM控制
2. **分层执行**：不是追求Agent数量，而是按实际需要划分执行单元
3. **独立验证**：预测登记、结算、校准形成完整闭环
4. **手机适配**：轻量本地 + 云端服务 + 断点恢复
5. **渐进扩展**：P0验证闭环 → P1按瓶颈拆分 → P2按价值扩展
